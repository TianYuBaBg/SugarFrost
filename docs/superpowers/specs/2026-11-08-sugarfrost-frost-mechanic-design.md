# 糖霜机制：把「霜」从状态提示升级成真机制

日期：2026-11-08
状态：已与用户确认（静态霜层 + 接触受热，36 张、1~3 层）

## 背景

第一版是 day-04-sheep 的 1:1 复刻：被压住的牌盖一层半透明霜，霜只表示「不可点」，不构成决策。
本次把霜做成独立机制，让「从哪儿开始拆」变成真选择，同时保留原有遮挡规则不变。

## 一、机制

- 每张牌新增 `frostLayers ∈ 0..3`，开局 36 张（全盘 1/3）带霜，层数分布 1 : 2 : 3 = 16 : 12 : 8（合计 68 层）。
- **带霜不可点**：点它只抖动 + 冰壳闪一下，不进卡槽、不消耗任何东西。
- **接触受热**：一张牌被取走（飞向卡槽那一刻），所有与它**原位置矩形最近距离 ≤ 12px** 且仍在牌堆上的牌 `frostLayers -= 1`（下限 0）。被压住的牌同样受热，等于拆上层时就在给下层化霜。
- 只有这一条热源：三连消除本身不再额外升温。
- 遮挡规则、7 格卡槽、胜负判定全部不变。

## 二、视觉语义

两种状态必须一眼区分：

| 状态 | 视觉 |
| --- | --- |
| 被压住 | 深色压暗罩（10% 深紫灰）+ 压暗描边，**不出现冰** |
| 带霜 | 边缘/四角结冰 + 冷色冰缘 + 右上角层数徽标（深蓝底白数字 1/2/3），中央留清 |
| 两者叠加 | 压暗 + 冰缘，含义是「够不着，且够到也要先化」 |

带霜刻意不在中央盖白：糖的种类必须一眼可辨，否则玩家没法规划「先化哪片冰」。层数数字用 `Graphics` 画的 7 段数码管烘焙进贴图，不用 `Text`（108 个 Text 会各自回读 canvas）。

融化反馈：点带霜牌时冰壳闪一下（alpha 1 → 0.45 两下）+ 卡片抖动；层数减一时换贴图并 `Back` 弹一下；减到 0 时冰壳淡出放大（`scale 1.16` + `alpha → 0`，240ms）。

## 三、保证有解

热源只由几何决定，与牌型无关，因此可以精确构造：

1. 先按原流程摆牌，推演合法清空顺序 `T`（108 张）。
2. 沿 `T` 模拟受热，得到每张牌的 `heatBudget`：在它自己被取走之前，会被多少次「相邻抽牌」加热。只统计当时仍在牌堆上的牌。
3. 发霜时强制 `frostLayers ≤ heatBudget`。于是轮到任何一张牌时，它累计受热次数 ≥ 层数，霜必然已归零。

推论：`heatBudget = 0` 的牌（早期被取的牌）永远不会带霜，所以保证路线 `T` 从头到尾可执行，「每局都能通」这一性质不被破坏。

发霜顺序：先从 `heatBudget ≥ 3` 里挑 8 张给 3 层，再从剩余 `heatBudget ≥ 2` 里挑 12 张给 2 层，最后从 `heatBudget ≥ 1` 里挑 16 张给 1 层；某档不够就顺延到下一档。层级候选都用 seeded rng 打乱，保证可复现。

## 四、数值

| 项 | 值 | 说明 |
| --- | --- | --- |
| 带霜牌数 | 36 | 108 的 1/3 |
| 层数分布 | 16 / 12 / 8 | 1 层 / 2 层 / 3 层，共 68 层 |
| 受热距离 | 12px | 矩形最近距离，逻辑像素 |
| 单次受热张数 | 4.4~4.8 | 实测：散卡重叠多，gap 4~12 差别很小 |
| 衰减曲线 | 36 → 26(10抽) → 18(20) → 10(30) → 4.5(40) | 12 局平均，照 `T` 走 |

调参入口全部在 `js/core/config.js` 的 `FROST_*`。

已知取舍：受热次数（全程 ~500）远多于总层数（68），所以霜集中在前半局，后半局退化回无霜的 day-04 手感。要让它撑满全场得靠动态结霜，本次明确不做（用户选了静态霜）。

## 五、架构

- 新增 `js/core/frost.js`（纯函数，可在 node 里跑）：
  - `rectGap(a, b)` 两个 AABB 的最近距离（相交为 0）
  - `heatTargets(cards, source, gap)` 受热目标（存活、非自己）
  - `applyHeat(cards, ids)` 扣层，返回 `[{id, from, to}]`
  - `computeHeatBudget(cards, order)` 供生成器用
  - `assignFrost(cards, order, rng)` 按预算发霜
- `js/core/LevelGenerator.js` 在算出 `T` 之后多调两步：`computeHeatBudget` → `assignFrost`；返回的卡多带 `frostLayers`。
- `js/art/CardArt.js`：`frost` 单图拆成 `frost1/frost2/frost3`（冰壳 + 冰点）与 `shade`（压暗罩）。
- `js/scene/GameScene.js`：
  - 卡片容器内多一个 `shade` 图层（遮挡用），`frost` 图层改由 `frostLayers` 驱动
  - `onCardTap` 增加带霜拦截 + 抖动
  - `pickCard` 里扣层并播融化动画
  - HUD 追加「霜 N」（剩余带霜牌数）
- `js/core/rules.js` 不改（遮挡仍只看几何）。

## 六、验证

- `tools/selftest.mjs` 新增：`rectGap` 边界、受热目标正确性、层数不超预算、36 张/层级分布、**沿 `T` 全流程模拟**（每张牌被点时 `frostLayers === 0`）、开局至少 6 张「可点且无霜」的牌。
- `tools/playthrough.mjs`：现在同时验证「照解序走，霜不会挡路」，108 次点击仍需全部成功。
- `tools/browser-check.mjs` 新增：点带霜牌不消耗（剩余张数不变、层数不变）；点相邻牌后邻居层数 -1；开局统计带霜数量。

## 七、风险与实测结论

- **画面变暗**：遮挡从浅霜改成压暗后整体偏灰。实测把压暗降到 10%，并在霜上保留「边缘结冰 + 中央留清」后，糖仍可辨；`frost` 全白 0.62 的版本会把带霜牌看成「空白牌」，已废弃。
- **层数表达**：小圆点表示 1/2/3 在 76px 卡面上会糊成一团；7 段数字方案在 390×844 实机上可读。
- **3 层霜是否太硬**：`heatBudget ≥ 3` 的牌每个种子有 60+ 张，8 张 3 层配额稳拿；照 `T` 走时全流程 0 次被霜拦（`playthrough.mjs` 108 次点击全通过）。
- **首屏枯燥**：实测开局可点 25 张里带霜 2~5 张，机制第一屏就能看见（`.tmp/start.png`）。
